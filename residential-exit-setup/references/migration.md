# 新旧出口迁移与回滚

## 并行迁移

1. 在旧线路仍可用时备份：VPS 的服务定义、受影响的代理配置、权限/所属用户、DNS 记录内容与 TTL、DDNS 设置；本地保存活动订阅、规则扩展、策略组选择。备份含凭据，访问权限最小化，不输出内容。
2. 新 VPS 使用单独的协议凭据、测试端口和临时 DNS 记录（如 `new-exit.xxx`），独立测试其公网入站、最终出口、DNS 和服务。临时域名只是稳定的地址名称，不是流量中转节点；IP 稳定时也可直接用 IP。
3. 为新出口创建独立 DDNS 更新器，不和旧服务器更新同一条记录。域名记录是否由 CDN 代理应按协议设计核对；普通 TCP 代理在 DNS-only 场景通常需要真实目标地址，不能假设 HTTP CDN 代理可转发任意 TCP。
4. 添加新客户端节点，不覆盖旧节点；如用户需要给朋友使用，分别检查共享配置是否真的包含新节点、分流规则及 DNS，避免分享机场主订阅或管理令牌。客户端本地增强规则不会自动进入对方配置。
5. 测试通过后按用户要求切换；变更前保存当前选择，记录新旧域名/IP/端口映射（私密保管），检测 TTL/客户端缓存与既有连接持续时间。若沿用原域名，先停旧 VPS 对该记录的 DDNS、确认其不会恢复，再让新 updater 接管；必要时核对并回滚 DNS 记录。
6. 观察一段合适时间，再经授权停旧机器、撤销旧凭据或删除旧配置。新旧共用出口、账号或资源的依赖关系未核实前不清理。

## 动态 IPv4 与 NAT

- DDNS 查询的两个公网 IP 服务仅能帮助核对**出站地址**，不证明入站 NAT 的公网映射地址相同。向服务商确认映射，对入站端口从外部实测；不能用出站 IP 自动覆盖入站记录，除非映射关系已证实。
- 若多个公网地址、共享 NAT 或供应商频繁调整映射，应使用供应商的映射状态/API 或指定地址来源；记录失败状态，绝不静默更新到不确定的地址。
- DDNS 令牌只授予必要的 DNS 编辑权限，限制 zone；不写入日志、命令行或示例。使用私有权限文件/凭据存储，验证 IP 格式、记录名称与 DNS-only 状态后更新，并读取确认。
- IPv4 A 记录、IPv6 AAAA 记录和 IPv6 硬编码节点应分别考虑；当前通过 A 记录更新不会自动修复 IPv6 节点。

## 回滚方案

- 修改前明确回滚触发条件：配置校验失败、服务未启动、管理路径丢失、目标连接或 DNS/业务验证失败。计划、备份、回滚程序和触发条件必须在真正更改之前可用。
- 远端变更通过将被修改的服务承载管理连接时，设置服务端独立 watchdog/定时器，在限时内未确认成功则恢复原配置并恢复服务；先验证定时器确已就绪。顺序修改多个服务，避免一起下线。
- 切换后检查实际公网端口、进程、日志和代表性用户访问；成功时记录校验结果并解除 watchdog。失败时恢复被修改文件、原权限与服务、客户端策略组和 DNS 记录；再次验证旧链路。
- 切换回旧记录时避免旧新 DDNS 双写，核对 DNS 缓存可能导致的短暂不一致。回滚并非删除备份；保留回滚材料，直到确认稳定并按用户要求处理。
