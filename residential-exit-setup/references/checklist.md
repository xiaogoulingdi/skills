# 新出口接入与测试清单

## 1. 接入前

- 记录用户目标：地区、是否一定要住宅 IPv4、独享或共享、日常业务、延迟目标、流量预算、迁移还是新增、允许的维护时间。线路目标应实测，不承诺某个上限。
- 客户端：确认实际活动订阅和节点选择；读取策略组、前置规则、DNS、系统代理/TUN、浏览器安全 DNS。识别订阅规则和用户本地覆写分别存放在哪里。
- 前置：获取可用协议、香港/日本节点名、DNS 与 UDP 能力、是否允许连接下游地址端口；只验证本任务需要的候选线路。
- VPS：从服务商面板与系统分别检查 OS、CPU 架构、软件、独立 IPv4/共享 NAT、IPv6、SSH 与实际公网端口映射；核对防火墙、安全组、端口占用及出入站地址。家庭 IP、独享 IP、动态 IP 和 NAT 是不同属性。
- 记录控制路径和恢复方式：服务商控制台、SSH、公网映射；避免唯一管理路径依赖将要重启的服务。

## 2. 部署及接入

- 选择与前置、客户端兼容的协议与传输，加密和身份认证、端口占用、供应商政策均需单独评估。示例 VMess/TCP 是历史选择，不代表自动适合新部署。
- 下载前核对官方发布、版本、架构、校验和及许可；最小开放必要端口；只读获取原服务状态并备份，再创建独立候选配置。不得覆盖未知现有服务。
- 用独立高位端口、临时目录和独立客户端核心测试；内网监听与正式公网开放需分别核对。运行官方配置语法测试，再验证可从前置到达入口。
- Clash 中将前置节点组和新出口显式串联，遵守当前客户端实际支持的格式；保留活动配置、现有自定义规则。客户端 `proxy-provider` 获取机场节点，不自动继承机场的分流 `rules`。
- 明确 UDP 支持能力；不能假设 TCP-only 链路能完整承载 UDP、QUIC、游戏或 WebRTC。若关闭 UDP，解释受影响业务并测试。
- 需要自动选择时建立并测试前置及出口健康检查；当前若选中固定节点或固定端口，注明未启用自动切换。几个端口若同一台 VPS，只能容忍部分端口故障。

## 3. DNS 的两层验证

- 先检查浏览器及客户端 DNS：Fake-IP/真实 IP、规则优先级、TCP/UDP 53、IPv6、浏览器自行 DoH 与 TUN 接管范围；bootstrap、节点域名解析与常规 DNS 作用不同。
- 检查 VPS 代理进程：目标域名是否转交服务端解析；区分本地 `/etc/resolv.conf` 与 Xray 内置 DNS。加密 DNS 连接验证 TLS 和服务端名称，不关闭证书校验；避免解析器域名自举循环。
- 在独立进程和端口上测试主、备 DNS、超时、无结果、IPv4/IPv6 策略、代表性域名与网站。使用失败时是否回退到系统 DNS要明确；安全优先的 Force 策略可能影响解析失败和仅 IPv6 网站，必须实测。
- 用同一台设备、同一浏览器在真实链路测试 DNS 检测网站。记录页面实际出现的解析器、运营商和地区；对地理数据库、任播、上游转发、DNS 缓存和扩展独立解析保留不确定性。未发现校园网解析器不等于全设备永不泄露。
- 网页 DNS 测试涉及多次随机子域名，必须以浏览器实际测试与运行时连接证据为主；单个 `whoami` 查询或 `fake-ip` 答复不足以证明完整链路。

## 4. 验收与证据

1. 逐端口证实入口映射、身份认证和代理转发；测试同一台 VPS 不同端口的故障边界。
2. 分别测本机→前置、前置→出口、端到端；统计多次 HTTPS 响应和错误，必要时区分白天与晚高峰。Ping 与测试网站性能不可互换。
3. 分别核对外网 IPv4、IPv6、地域与 ASN；一个 HTTP 200、一个 IP 数据库或住宅标签都不足以保证 AI 风控表现、独享或运营商属性。
4. 检查具体站点的规则匹配、国内直连和特殊站点路径；记录 DNS 位置、浏览器 WebRTC 实测及其不完整的范围。
5. 验证服务重启及配置持久性，DNS 动态更新、变更后传播和回滚；记录实际测试与未验证项。运行期运行正常不等同于已经做过系统重启或模拟 IP 变化测试。
